## 写作范围

文档的价值是保存无法仅靠阅读单个实现文件可靠还原的意图。

| 应记录 | 应链接到事实源 |
| --- | --- |
| 模块责任与依赖方向 | 模块和类的完整列表 |
| 状态机与失败恢复语义 | 枚举字段与序列化文本 |
| 事务、原子性和持久化边界 | NBT/JSON 字段清单 |
| 算法必须保持的不变量 | 具体常量与配置默认值 |
| 需要多模块共同遵守的约束 | 依赖版本、配方、标签与翻译原文 |

## 表达方式

- 每节只处理一个主题，使用短标题形成清晰分区。
- 映射、对照、状态与责任优先使用表格。
- 流程仅在顺序本身构成约束时使用短步骤或流程图。
- 正文保持短小；能够通过文件链接表达的事实不重复转述。
- 只描述当前有效设计。历史内容只有在仍承担兼容责任时才保留。
- 使用正向约束表达当前模型，不建立已退出项目的方案清单。

## 规格准入

新增 `spec` 至少应满足一项：

| 条件 | 典型问题 |
| --- | --- |
| 跨模块协议 | 谁拥有入口、目标或持久化数据 |
| 事务边界 | 失败发生时哪些状态允许提交 |
| 失败恢复 | 重试、暂停、回滚或人工恢复如何区分 |
| 非显然算法 | 无损换算、公平调度、有界搜索 |
| 可选依赖隔离 | 第三方生命周期与 side 类加载边界 |

功能只是拥有若干字段、按钮、槽位或配方时，不建立开发专题。

## 更新规则

1. 先修改真正的事实源。
2. 检查受影响的骨干文档与规格是否仍表达正确意图。
3. 删除失效内容，不在当前文档中保留迁移过程的叙述。
4. 新事实若能从代码直接看出，只补导航；只有形成稳定约束时才补正文。
5. 合并相邻主题，避免为单个类、资源或 Integration 重复建立说明书。
